# Контроллеры

:::info[Оригинал]
[docs.nestjs.com — Controllers](https://docs.nestjs.com/controllers) · NestJS 12.1 · перевод от 01.10.2026
:::

Контроллеры отвечают за обработку входящих **запросов** и отправку **ответов** клиенту.

![Контроллеры](/img/nestjs/controllers-1.png#themed)

Задача контроллера — обрабатывать определённые запросы к приложению. Механизм **маршрутизации** определяет, какой контроллер обработает каждый запрос. Обычно у контроллера несколько маршрутов, и каждый маршрут может выполнять своё действие.

Чтобы создать простой контроллер, используются классы и **декораторы**. Декораторы связывают классы с нужными метаданными, по которым Nest строит карту маршрутизации, сопоставляющую запросы с соответствующими контроллерами.

:::tip[Подсказка]
Чтобы создать CRUD-контроллер со встроенной валидацией{/* TODO-LINK: https://docs.nestjs.com/application/validation — Application → Validation */}, используйте CRUD-генератор{/* TODO-LINK: https://docs.nestjs.com/recipes/crud-generator — Recipes → CRUD generator */} CLI: `nest g resource [name]`.
:::

## Маршрутизация {/* #routing */}

В следующем примере используется декоратор `@Controller()`, который **обязателен** для определения простого контроллера, с необязательным префиксом пути маршрута `cats`. Префикс пути в декораторе `@Controller()` группирует связанные маршруты и избавляет от повторяющегося кода. Например, чтобы сгруппировать маршруты для работы с сущностями котов под путём `/cats`, укажите префикс `cats` в декораторе `@Controller()`. Тогда не придётся повторять эту часть пути для каждого маршрута в файле.

```ts title="cats.controller.ts"
import { Controller, Get } from '@nestjs/common';

@Controller('cats')
export class CatsController {
  @Get()
  findAll(): string {
    return 'This action returns all cats';
  }
}
```

:::tip[Подсказка]
Чтобы создать контроллер с помощью CLI, выполните команду `$ nest g controller [name]`.
:::

Декоратор HTTP-метода `@Get()` перед методом `findAll()` указывает Nest создать обработчик для определённого эндпоинта. Эндпоинт определяется HTTP-методом запроса (в данном случае GET) и путём маршрута. Путь маршрута обработчика складывается из (необязательного) префикса, объявленного для контроллера, **и** пути, указанного в декораторе метода. Поскольку в примере задан префикс (`cats`), а в декораторе метода путь не указан, Nest сопоставит с этим обработчиком запросы `GET /cats`.

Если бы в декораторе метода тоже был указан путь, например `@Get('breed')`, итоговый маршрут был бы `GET /cats/breed`.

Когда приходит запрос `GET /cats`, Nest направляет его в пользовательский метод `findAll()`. Имя метода произвольное: метод для привязки маршрута объявить нужно, но его имя для Nest ничего не значит.

Этот метод возвращает код статуса 200 вместе с ответом — в данном случае строкой. Чтобы объяснить почему, нужно рассказать о двух **разных** способах работы с ответами, которые предоставляет Nest:

| Способ                         | Описание |
| ------------------------------ | -------- |
| Стандартный (рекомендуемый)    | При этом встроенном способе, если обработчик маршрута возвращает JavaScript-объект или массив, он **автоматически** сериализуется в JSON. Если возвращается примитив JavaScript (например, `string`, `number`, `boolean`), Nest отправляет значение без попытки сериализации. Поэтому работа с ответом простая: верните значение, а остальное Nest сделает сам.<br /><br />**Код статуса** ответа по умолчанию — 200, кроме POST-запросов, для которых используется 201. Это поведение можно изменить, добавив декоратор `@HttpCode(...)` на уровне обработчика (см. [Код статуса](#status-code)). |
| Специфичный для библиотеки     | Можно использовать [объект ответа](https://expressjs.com/en/api.html#res) конкретной библиотеки (например, Express), внедряемый декоратором `@Res()` в сигнатуру обработчика маршрута (например, `findAll(@Res() response)`). Этот способ позволяет пользоваться нативными методами обработки ответа, которые предоставляет этот объект. Например, в Express ответ можно сформировать кодом вида `response.status(200).send()`. |

:::warning[Внимание]
Nest определяет, использует ли обработчик `@Res()` или `@Next()`, — это означает, что выбран способ, специфичный для библиотеки. Если оба способа используются одновременно, стандартный способ для этого маршрута **автоматически отключается** и перестаёт работать как ожидается. Чтобы совместить их (например, внедрить объект ответа только для установки cookies или заголовков, а остальное оставить фреймворку), установите опцию `passthrough` в `true` в декораторе `@Res({ passthrough: true })`.
:::

## Объект запроса {/* #request-object */}

Обработчикам часто нужен доступ к деталям **запроса** клиента. Nest предоставляет доступ к [объекту запроса](https://expressjs.com/en/api.html#req) нижележащей платформы (по умолчанию Express). Чтобы получить его, добавьте декоратор `@Req()` в сигнатуру обработчика — он указывает Nest внедрить этот объект.

```ts title="cats.controller.ts"
import { Controller, Get, Req } from '@nestjs/common';
import type { Request } from 'express';

@Controller('cats')
export class CatsController {
  @Get()
  findAll(@Req() request: Request): string {
    return 'This action returns all cats';
  }
}
```

:::tip[Подсказка]
Чтобы пользоваться типами `express` (как в параметре `request: Request` выше), установите пакет `@types/express`.
:::

Объект запроса представляет HTTP-запрос и содержит свойства для строки запроса, параметров маршрута, HTTP-заголовков и тела (см. [документацию Express](https://expressjs.com/en/api.html#req)). В большинстве случаев обращаться к этим свойствам вручную не нужно. Вместо этого используйте специальные декораторы, например `@Body()` или `@Query()`, которые доступны из коробки. В таблице ниже перечислены эти декораторы и платформенные объекты, которые они представляют.

| Декоратор                          | Объект |
| ---------------------------------- | ------ |
| `@Request(), @Req()`               | `req` |
| `@Response(), @Res()`\*            | `res` |
| `@Next()`                          | `next` |
| `@Session()`                       | `req.session` |
| `@Param(key?: string)`             | `req.params` / `req.params[key]` |
| `@Body(key?: string)`              | `req.body` / `req.body[key]` |
| `@Query(key?: string)`             | `req.query` / `req.query[key]` |
| `@Headers(name?: string)`          | `req.headers` / `req.headers[name]` |
| `@Cookies(name?: string)`          | cookies запроса / cookie с именем `name` (см. Cookies{/* TODO-LINK: https://docs.nestjs.com/http/cookies — HTTP → Cookies */}) |
| `@SignedCookies(name?: string)`    | проверенные подписанные cookies / подписанная cookie с именем `name` |
| `@Ip()`                            | `req.ip` |
| `@HostParam()`                     | `req.hosts` |

<sup>\*</sup> Для совместимости с типами разных HTTP-платформ (например, Express и Fastify) Nest предоставляет декораторы `@Res()` и `@Response()`. `@Res()` — это псевдоним для `@Response()`. Оба напрямую дают доступ к нативному объекту `response` нижележащей платформы. При их использовании также установите типы для нижележащей библиотеки (например, `@types/express`), чтобы пользоваться ими в полной мере. Когда вы внедряете `@Res()` или `@Response()` в обработчик маршрута, вы переводите Nest в **режим, специфичный для библиотеки**, для этого обработчика и берёте управление ответом на себя. В этом случае вы обязаны отправить ответ, вызвав метод объекта `response` (например, `res.json(...)` или `res.send(...)`), иначе запрос зависнет.

`@Body()`, `@Query()`, `@Param()` и `@RawBody()` также принимают объект опций со свойствами `schema` и `pipes`. Это позволяет прикреплять схемы, совместимые со [Standard Schema](https://standardschema.dev/), — например, созданные с помощью Zod, Valibot или ArkType, — прямо к параметрам маршрута.

```ts
@Post()
create(@Body({ schema: createCatSchema }) createCatDto: CreateCatDto) {
  return this.catsService.create(createCatDto);
}

@Get(':id')
findOne(@Param('id', { schema: z.coerce.number().int().positive() }) id: number) {
  return this.catsService.findOne(id);
}
```

Сами по себе эти декораторы лишь прикрепляют схему как метаданные. Чтобы выполнять по ней валидацию, зарегистрируйте встроенный `StandardSchemaValidationPipe` или собственный пайп, который читает `metadata.schema`.

:::tip[Подсказка]
О том, как создавать собственные декораторы, читайте в главе «Пользовательские декораторы маршрутов»{/* TODO-LINK: https://docs.nestjs.com/custom-decorators — Overview → Custom decorators */}.
:::

## Ресурсы {/* #resources */}

Ранее мы определили эндпоинт для получения ресурса котов (маршрут **GET**). Обычно также нужен эндпоинт для создания новых записей. Добавим обработчик **POST**:

```ts title="cats.controller.ts"
import { Controller, Get, Post } from '@nestjs/common';

@Controller('cats')
export class CatsController {
  @Post()
  create(): string {
    return 'This action adds a new cat';
  }

  @Get()
  findAll(): string {
    return 'This action returns all cats';
  }
}
```

Nest предоставляет декораторы для всех стандартных HTTP-методов: `@Get()`, `@Post()`, `@Put()`, `@Delete()`, `@Patch()`, `@Options()`, `@Head()` и `@QueryMethod()`. Последний соответствует методу `QUERY`; он называется `QueryMethod`, чтобы не конфликтовать с декоратором параметра `@Query()`. Кроме того, `@All()` определяет эндпоинт, который обрабатывает их все.

## Wildcard-маршруты {/* #route-wildcards */}

Nest также поддерживает маршруты по шаблону. Например, звёздочка (`*`) в конце пути работает как wildcard (подстановочный символ), совпадающий с любой комбинацией символов. В следующем примере метод `findAll()` выполняется для любого маршрута, начинающегося с `abcd/`, независимо от количества символов после него.

```ts
@Get('abcd/*')
findAll() {
  return 'This route uses a wildcard';
}
```

Путь маршрута `'abcd/*'` совпадает с `abcd/`, `abcd/123`, `abcd/abc` и так далее. В строковых путях дефис (`-`) и точка (`.`) интерпретируются буквально.

Этот подход работает и с Express, и с Fastify. Однако в Express v5 маршрутизация стала строже: в чистом Express wildcard должен быть именованным, чтобы маршрут работал (например, `abcd/{*splat}`, где `splat` — произвольное имя wildcard-параметра без особого смысла). Поскольку Nest предоставляет слой совместимости для Express, вы по-прежнему можете использовать неименованную звёздочку (`*`) как wildcard.

Для звёздочек в **середине маршрута** Express требует именованные wildcard'ы (например, `ab{*splat}cd`), а Fastify их не поддерживает вовсе.

## Конфликты маршрутов и порядок разрешения {/* #route-conflicts-and-resolution-order */}

Nest регистрирует маршруты в порядке объявления. Поэтому на адаптерах, чувствительных к порядку (например, на адаптере Express по умолчанию), параметризованный маршрут может незаметно перекрыть более конкретный:

```ts
@Controller('users')
export class UsersController {
  @Get(':id')
  findOne() {}

  @Get('me') // сюда не попасть: `:id` первым совпадает с "me"
  findMe() {}
}
```

Это легко пропустить: приложение запускается без предупреждений, а проблема проявляется только во время работы, когда запрос попадает не в тот обработчик. Пайпы вроде `ParseIntPipe` здесь не помогут, потому что маршрутизация выбирает обработчик *до* запуска любых пайпов.

В NestJS v12 появились два необязательных свойства `NestApplicationOptions`, которые защищают от этого. Оба по умолчанию сохраняют прежнее поведение, так что существующие приложения не затронуты, пока вы их не включите.

**`routeConflictPolicy`** включает диагностику при запуске. Для каждого вида конфликта задаётся уровень серьёзности: `'off'` (по умолчанию), `'warn'` или `'error'`:

```ts
const app = await NestFactory.create(AppModule, {
  routeConflictPolicy: { duplicate: 'error', shadow: 'warn' },
});
```

| Вид конфликта | Описание |
| ------------- | -------- |
| `duplicate`   | Два маршрута с одинаковыми методом, путём, хостом и версией. |
| `shadow`      | Два шаблона маршрутов могут совпасть с одним и тем же запросом (например, `/users/me` и `/users/:id`). |

При `'error'` все конфликтующие пары собираются в одно исключение `RouteConflictException`, которое выбрасывается при инициализации приложения (в `app.init()` или в `app.listen()`, если `init()` явно не вызывается). Так вы видите все конфликты сразу, а не по одному за перезапуск.

**`routeResolutionStrategy`** управляет порядком регистрации. Значение `'specificity'` регистрирует сначала самые конкретные маршруты (литеральные сегменты важнее параметризованных, а те — важнее wildcard'ов), поэтому пример выше работает независимо от порядка объявления:

```ts
const app = await NestFactory.create(AppModule, {
  routeResolutionStrategy: 'specificity',
});
```

Значение по умолчанию — `'declaration'`, оно сохраняет прежнее поведение.

:::tip[Подсказка]
Кроме политики `duplicate`, эти опции имеют значение только на адаптерах, где порядок регистрации влияет на сопоставление. `ExpressAdapter` чувствителен к порядку, а `FastifyAdapter` — нет, потому что его роутер (`find-my-way`) уже ранжирует маршруты по конкретности. На Fastify политика `shadow` ничего не делает и сортировка `'specificity'` не имеет эффекта, а политика `duplicate` учитывается на обоих адаптерах. Типы `RouteConflictPolicy`, `RouteConflictPolicyLevel` и `RouteResolutionStrategy` экспортируются из `@nestjs/common`.
:::

## Код статуса {/* #status-code */}

Как уже говорилось, **код статуса** ответа по умолчанию — **200**, кроме POST-запросов, для которых по умолчанию **201**. Это поведение можно изменить декоратором `@HttpCode(...)` на уровне обработчика.

```ts
@Post()
@HttpCode(204)
create() {
  return 'This action adds a new cat';
}
```

:::tip[Подсказка]
Импортируйте `HttpCode` из пакета `@nestjs/common`.
:::

Часто код статуса не статичен, а зависит от разных факторов. В таком случае используйте **объект ответа**, специфичный для библиотеки (внедряемый через `@Res()`), или, в случае ошибки, выбросьте исключение.

## Заголовки ответа {/* #response-headers */}

Чтобы задать собственный заголовок ответа, используйте декоратор `@Header()` или объект ответа, специфичный для библиотеки (и вызовите `res.header()` напрямую).

```ts
@Post()
@Header('Cache-Control', 'no-store')
create() {
  return 'This action adds a new cat';
}
```

:::tip[Подсказка]
Импортируйте `Header` из пакета `@nestjs/common`.
:::

## Перенаправление {/* #redirection */}

Чтобы перенаправить ответ на определённый URL, используйте декоратор `@Redirect()` или объект ответа, специфичный для библиотеки (и вызовите `res.redirect()` напрямую).

`@Redirect()` принимает два необязательных аргумента: `url` и `statusCode`. Если `statusCode` не указан, по умолчанию используется `302` (`Found`).

```ts
@Get()
@Redirect('https://nestjs.com', 301)
```

:::tip[Подсказка]
Чтобы определять код статуса HTTP или URL перенаправления динамически, верните объект, соответствующий интерфейсу `HttpRedirectResponse` (экспортируется из `@nestjs/common`).
:::

Возвращённые значения переопределяют аргументы, переданные в декоратор `@Redirect()`. Например:

```ts
@Get('docs')
@Redirect('https://docs.nestjs.com', 302)
getDocs(@Query('version') version) {
  if (version && version === '5') {
    return { url: 'https://docs.nestjs.com/v5/' };
  }
}
```

## Параметры маршрута {/* #route-parameters */}

Маршруты со статическими путями не подходят, когда нужно принимать **динамические данные** как часть запроса (например, `GET /cats/1`, чтобы получить кота с id `1`). Чтобы определить маршрут с параметрами, добавьте в путь маршрута **токены** параметров — они захватывают динамические значения из URL, как показано в декораторе `@Get()` в примере ниже. Затем к этим параметрам маршрута можно обратиться с помощью декоратора `@Param()`, добавленного в сигнатуру метода.

:::tip[Подсказка]
Объявляйте маршруты с параметрами после статических путей, чтобы параметризованный путь не перехватывал трафик, предназначенный для статического. Опции, которые обнаруживают такую ситуацию при запуске или решают её за вас, описаны в разделе [Конфликты маршрутов и порядок разрешения](#route-conflicts-and-resolution-order).
:::

```ts
@Get(':id')
findOne(@Param() params: any): string {
  console.log(params.id);
  return `This action returns a #${params.id} cat`;
}
```

Декоратор `@Param()` декорирует параметр метода (`params` в примере выше), делая параметры **маршрута** доступными как свойства этого параметра внутри метода. Как видно из кода, к параметру `id` обращаются через `params.id`. Можно также передать в декоратор конкретный токен параметра и обращаться к параметру маршрута в теле метода напрямую по имени.

:::tip[Подсказка]
Импортируйте `Param` из пакета `@nestjs/common`.
:::

```ts
@Get(':id')
findOne(@Param('id') id: string): string {
  return `This action returns a #${id} cat`;
}
```

## Маршрутизация по поддоменам {/* #sub-domain-routing */}

Декоратор `@Controller()` может принимать опцию `host`, чтобы требовать совпадения HTTP-хоста входящих запросов с определённым значением.

```ts title="admin.controller.ts"
@Controller({ host: 'admin.example.com' })
export class AdminController {
  @Get()
  index(): string {
    return 'Admin page';
  }
}
```

:::warning[Внимание]
Поскольку **Fastify** не поддерживает вложенные роутеры, при использовании маршрутизации по поддоменам используйте адаптер Express по умолчанию.
:::

Как и `path` маршрута, опция `host` может использовать токены, чтобы захватывать динамическое значение в этой позиции имени хоста, — как токен параметра хоста в декораторе `@Controller()` ниже. К объявленным так параметрам хоста можно обратиться с помощью декоратора `@HostParam()`, добавленного в сигнатуру метода.

```ts title="account.controller.ts"
@Controller({ host: ':account.example.com' })
export class AccountController {
  @Get()
  getInfo(@HostParam('account') account: string) {
    return account;
  }
}
```

## Разделение состояния {/* #state-sharing */}

Разработчиков, пришедших из других языков программирования, может удивить, что в Nest почти всё разделяется между входящими запросами. Это касается таких ресурсов, как пул соединений с базой данных, singleton-сервисы с глобальным состоянием и многое другое. Node.js не следует многопоточной stateless-модели «запрос/ответ», в которой каждый запрос обрабатывается отдельным потоком. Поэтому использовать singleton-экземпляры в Nest полностью **безопасно**.

Тем не менее в некоторых пограничных случаях контроллерам может понадобиться время жизни, привязанное к запросу: например, кеширование на уровне запроса в GraphQL-приложениях, отслеживание запросов или multi-tenancy (мультиарендность). О том, как этим управлять, читайте в главе «Области внедрения»{/* TODO-LINK: https://docs.nestjs.com/fundamentals/injection-scopes — Fundamentals → Injection scopes */}.

## Асинхронность {/* #asynchronicity */}

Современный JavaScript активно использует **асинхронную** обработку данных, и Nest полностью поддерживает `async`-функции. `async`-функция всегда возвращает `Promise`, поэтому обработчик маршрута может вернуть отложенное значение, которое Nest разрешит автоматически:

```ts title="cats.controller.ts"
@Get()
async findAll(): Promise<any[]> {
  return [];
}
```

Обработчики маршрутов также могут возвращать [observable-потоки](https://rxjs.dev/guide/observable) RxJS. Nest подписывается на поток внутри себя и разрешает последнее отправленное значение, когда поток завершится.

```ts title="cats.controller.ts"
@Get()
findAll(): Observable<any[]> {
  return of([]);
}
```

Оба подхода допустимы — выбирайте тот, что лучше подходит под ваши задачи.

## Тело запроса {/* #request-payloads */}

Обработчик POST-маршрута из предыдущего примера не принимал никаких параметров от клиента. Исправим это, добавив декоратор `@Body()`.

Прежде чем продолжить (если вы используете TypeScript), нужно определить схему **DTO** (Data Transfer Object, объект передачи данных). DTO — это объект, который описывает форму данных, передаваемых по сети. Схему DTO можно описать с помощью интерфейсов **TypeScript** или обычных классов, но рекомендуется использовать **классы**. Классы — часть стандарта JavaScript ES6, поэтому в скомпилированном JavaScript они сохраняются как реальные сущности. Интерфейсы TypeScript, напротив, удаляются при транспиляции, и Nest не может обратиться к ним во время выполнения. Это важно, потому что такие возможности, как **пайпы**, опираются на доступ к метатипу переменных во время выполнения, а это возможно только с классами.

Создайте класс `CreateCatDto`:

```ts title="create-cat.dto.ts"
export class CreateCatDto {
  name: string;
  age: number;
  breed: string;
}
```

У него три базовых свойства. Теперь новый DTO можно использовать в `CatsController`:

```ts title="cats.controller.ts"
@Post()
async create(@Body() createCatDto: CreateCatDto) {
  return 'This action adds a new cat';
}
```

:::tip[Подсказка]
`ValidationPipe` умеет отфильтровывать свойства, которые обработчик маршрута получать не должен. Вы составляете белый список допустимых свойств, и любое свойство вне его автоматически удаляется из итогового объекта. В примере с `CreateCatDto` белый список состоит из свойств `name`, `age` и `breed`. Подробнее — в разделе «Удаление свойств»{/* TODO-LINK: https://docs.nestjs.com/application/validation#stripping-properties — Application → Validation → Stripping properties */}.
:::

## Query-параметры {/* #query-parameters */}

Чтобы извлечь query-параметры (параметры строки запроса) из входящих запросов, используйте декоратор `@Query()`.

Рассмотрим маршрут, который фильтрует список котов по query-параметрам, например `age` и `breed`. Сначала определим query-параметры в `CatsController`:

```ts title="cats.controller.ts"
@Get()
async findAll(@Query('age') age: number, @Query('breed') breed: string) {
  return `This action returns all cats filtered by age: ${age} and breed: ${breed}`;
}
```

В этом примере декоратор `@Query()` извлекает значения `age` и `breed` из строки запроса. Например, запрос:

```text
GET /cats?age=2&breed=Persian
```

даст `age`, равный `'2'`, и `breed`, равный `'Persian'`. Значения query-параметров приходят строками, и одной аннотации типа `number` недостаточно для их преобразования. Чтобы получить число, примените пайп, например `ParseIntPipe` (см. «Пайпы»{/* TODO-LINK: https://docs.nestjs.com/pipes — Overview → Pipes */}).

Если приложению нужно обрабатывать более сложные query-параметры, например вложенные объекты или массивы:

```text
?filter[where][name]=John&filter[where][age]=30
?item[]=1&item[]=2
```

настройте HTTP-адаптер (Express или Fastify) на использование подходящего парсера строки запроса. В Express используйте парсер `extended`, который поддерживает сложные объекты запроса:

```ts title="main.ts"
const app = await NestFactory.create<NestExpressApplication>(AppModule);
app.set('query parser', 'extended');
```

В Fastify используйте опцию `querystringParser`:

```ts title="main.ts"
const app = await NestFactory.create<NestFastifyApplication>(
  AppModule,
  new FastifyAdapter({
    querystringParser: (str) => qs.parse(str),
  }),
);
```

:::tip[Подсказка]
`qs` — парсер строки запроса с поддержкой вложенности и массивов. Установите его командой `npm install qs`.
:::

## Наблюдение за маршрутами в продакшене {/* #observing-routes-in-production */}

Контроллер, который идеально работает на вашей машине, под реальной нагрузкой может вести себя совсем иначе. В продакшене вопрос никогда не звучит как «работает ли этот маршрут?» — скорее «почему `GET /cats/:id` после деплоя во вторник стал отвечать за 900 мс вместо 40 мс, и это происходит со всеми запросами или с одним невезучим тенантом?»

Обработчики маршрутов — естественная единица для ответа на этот вопрос, и [NestJS Observe](https://www.observe.nestjs.com/) собирает отчёты именно в этих единицах. Поскольку SDK `@nestjs/observe` встраивается в собственный жизненный цикл запроса Nest, а не оборачивает HTTP-сервер, каждое измерение помечается шаблоном маршрута, который вы объявили (`GET /cats/:id`, а не 10 000 разных URL). Поэтому каждый маршрут — это одна строка, которую можно сортировать, строить по ней графики и настраивать алерты:

```ts
const app = await NestFactory.create(AppModule, {
  instrument: ObserveInstrument,
});
```

Вместе с импортом `ObserveModule.forRoot()` в корневой модуль — это вся интеграция. Дальше медленный маршрут находится в три клика: отсортируйте список маршрутов по p95; откройте операцию, чтобы увидеть, постоянна регрессия или проявляется всплесками и началась ли она с релиза; затем откройте одно медленное выполнение и изучите его waterfall-диаграмму, чтобы понять, какой контроллер, метод сервиса или запрос занял время. Время учитывается по **классу и методу** за вычетом времени ожидания (`await`), поэтому `CatsService.findOne()`, который тратит 800 мс в собственном коде, сразу отличим от `CatsService.findOne()`, который 800 мс ждёт базу данных.

Как всё настроить — в главе «Observability»{/* TODO-LINK: https://docs.nestjs.com/observability/overview — Observability → Overview */}, а полный путь от алерта до отдельного запроса — в главе «Dashboard»{/* TODO-LINK: https://docs.nestjs.com/observability/dashboard — Observability → Dashboard */}.

## Полный пример ресурса {/* #full-resource-sample */}

В следующем примере используется несколько доступных декораторов для создания простого контроллера. Контроллер предоставляет несколько методов для доступа к внутренним данным и их изменения.

```ts title="cats.controller.ts"
import { Controller, Get, Query, Post, Body, Put, Param, Delete } from '@nestjs/common';
import { CreateCatDto, UpdateCatDto, ListAllEntities } from './dto.js';

@Controller('cats')
export class CatsController {
  @Post()
  create(@Body() createCatDto: CreateCatDto) {
    return 'This action adds a new cat';
  }

  @Get()
  findAll(@Query() query: ListAllEntities) {
    return `This action returns all cats (limit: ${query.limit} items)`;
  }

  @Get(':id')
  findOne(@Param('id') id: string) {
    return `This action returns a #${id} cat`;
  }

  @Put(':id')
  update(@Param('id') id: string, @Body() updateCatDto: UpdateCatDto) {
    return `This action updates a #${id} cat`;
  }

  @Delete(':id')
  remove(@Param('id') id: string) {
    return `This action removes a #${id} cat`;
  }
}
```

:::tip[Подсказка]
В Nest CLI есть генератор (schematic), который автоматически создаёт **весь шаблонный код**, чтобы не писать его вручную. Подробнее — в рецепте «CRUD-генератор»{/* TODO-LINK: https://docs.nestjs.com/recipes/crud-generator — Recipes → CRUD generator */}.
:::

## Запуск {/* #getting-up-and-running */}

Даже когда `CatsController` полностью определён, Nest пока о нём не знает и не создаст экземпляр этого класса.

Контроллеры всегда должны принадлежать модулю, поэтому мы указываем массив `controllers` в декораторе `@Module()`. Поскольку, кроме корневого `AppModule`, других модулей мы не определяли, зарегистрируем `CatsController` в нём:

```ts title="app.module.ts"
import { Module } from '@nestjs/common';
import { CatsController } from './cats/cats.controller.js';

@Module({
  controllers: [CatsController],
})
export class AppModule {}
```

Благодаря метаданным, прикреплённым к классу модуля через декоратор `@Module()`, Nest может определить, какие контроллеры нужно подключить.

## Подход, специфичный для библиотеки {/* #library-specific-approach */}

До сих пор мы рассматривали стандартный для Nest способ работы с ответами. Альтернатива — использовать [объект ответа](https://expressjs.com/en/api.html#res) конкретной библиотеки, внедряемый декоратором `@Res()`. Чтобы показать разницу, перепишем `CatsController` так:

```ts
import { Controller, Get, Post, Res, HttpStatus } from '@nestjs/common';
import type { Response } from 'express';

@Controller('cats')
export class CatsController {
  @Post()
  create(@Res() res: Response) {
    res.status(HttpStatus.CREATED).send();
  }

  @Get()
  findAll(@Res() res: Response) {
    res.status(HttpStatus.OK).json([]);
  }
}
```

Этот подход даёт больше гибкости, предоставляя полный контроль над объектом ответа (например, управление заголовками и доступ к возможностям конкретной библиотеки), но пользоваться им нужно осторожно. В целом он менее понятен и имеет недостатки. Главный из них — код становится зависимым от платформы, поскольку разные нижележащие библиотеки могут предоставлять разные API у объекта ответа. Кроме того, усложняется тестирование: среди прочего придётся мокать объект ответа.

Вдобавок при этом подходе теряется совместимость с возможностями Nest, которые опираются на стандартную обработку ответа, например с интерсепторами и декораторами `@HttpCode()` / `@Header()`. Чтобы решить эту проблему, включите опцию `passthrough`:

```ts
@Get()
findAll(@Res({ passthrough: true }) res: Response) {
  res.status(HttpStatus.OK);
  return [];
}
```

Так вы можете работать с нативным объектом ответа (например, устанавливать cookies или заголовки в зависимости от условий), а остальное оставить фреймворку.
